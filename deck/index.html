The Ratchet Principle.

Every agent mistake becomes a permanent rule. A failure isn't a bug to swat — it's a constraint to encode. The harness only tightens; it never loosens. That's what makes it a learning system rather than a pile of prompts, and why it compounds while prompts evaporate.

"Every agent mistake becomes a permanent rule … an ever-tightening feedback system shaped by actual failure history."

Addy Osmani, Agent Harness Engineering

In this repo the ratchet has an address: knowledge-base/learnings/ captures the failure, knowledge-base/decisions/ records the rule it became. We'll write one back, live, in Act III.
This is the slide that turns "harness" from noun into verb. The mechanism: when an agent errors, you don't just fix the code — you engineer the environment so that class of error can't recur, and that fix is permanent. A ratchet only turns one way. ACT II· Concepts· 02 / 04

Dynamic workflows:
orchestration as code.

A workflow lifts the plan out of Claude's turn-by-turn reasoning and into a JS script. Isolated contexts, resumable, repeatable quality — same orchestration every run.

phase() parallel( agent × N ) pipeline() synthesis agent()

“Workflows move the orchestration plan out of Claude's turn-by-turn reasoning and into code.” — Claude Code docs

Claude Code feature dynamic workflowisolated context

Vocabulary slide — one mental model, ≤2.5 min. Four primitives: agent() spawns one, parallel() fans out (up to 16 concurrent), pipeline() chains output→input, phase() groups work with token/time budgets. The whole script is "readable, reviewable, rerunnable, and repeatable quality" (Claude Code docs) — intermediate results live in script variables, NOT in Claude's context window, so the session stays responsive. CRITICAL LABEL: this is the JS-primitive sense of "workflow" — a Claude Code feature, shown via the `ultracode` keyword or the bundled `/deep-research`. It is NOT Aurora's gated `workflows/*.md` process specs (those come in Act III). Hence the badge-soft. Say it once, clearly, so the two senses never blur.
ACT II· Concepts· 02 / 04

Why code beats turn-by-turn.

Turn-by-turn orchestration has three predictable failure modes. A workflow doesn't coach them away — it makes them structurally impossible by writing the plan down.

Agentic laziness

Claude stops before finishing complex, multi-part tasks.

Self-preferential bias

Claude favors its own results when verification is needed.

Goal drift

Fidelity is lost across extended interactions.

The fix isn't a better prompt — it's structural prevention: an independent verifier, then an adversarial review agent that asks “which claims survived scrutiny?” Built-in example: /deep-research.

“Repeatable quality patterns — e.g. adversarial review, independent verification — that scale to hundreds of agents.” · failure modes: “agentic laziness… self-preferential bias… goal drift.” — Claude Code docs · “A harness for every task”

This is the WHY behind slide 9 — don't skip it, it's where the room nods. The three failure modes are real and named in the docs: laziness (stops early), self-bias (grades its own homework), goal drift (forgets the point over a long thread). Turn-by-turn can't fix these because the plan only exists in the conversation. A workflow writes the plan as code, so the adversarial-review step ALWAYS runs and the verifier is ALWAYS independent — you get the same quality on run 1 and run 100. `/deep-research` is the shippable proof: fan out searches, fetch sources, then adversarially verify and DROP the claims that didn't survive. Still a Claude Code feature, not an Aurora workflow.

Export your context to markdown files in a folder you control. Any agent can read them. Any model can operate on them. Git versions every change. Your knowledge compounds instead of evaporating.

markdown you ownmodel-agnostic git-versionedcompounds

“If something isn't in context at runtime, it doesn't exist for the agent.” · The model is not the moat — your context is. — life-os memory-base findings · CLAUDE.md, line 7

This is where the Act I motif ("the model is not the moat — your context is") gets its mechanism. Hot vs. cold context —
and the map between them.

Hot · right now

hot.md — < 5 KB, updated weekly. The current decision frame, blockers, next moves. Agents read this first.

Cold · authority & history

Resources/, learnings, decisions, transcripts — evergreen, large, rarely edited. Read on demand, when an agent needs justification.

The map agents traverse: PARA folders give spatial memory · Maps of Content (02-Atlas/*.md) index each domain · [[wikilinks]] make a backlink graph an agent can walk to find every page that references an idea.

Read order: “hot.md first for current context, index.md second for navigation.” · Hot < 5 KB, read first; cold is everything else. — life-os WIKI.md · Obsidian MOC + PARA findings

The single most useful mechanic in the whole memory-base story. The agent's read order on opening the vault: (1) WIKI.md learns "hot.md first, index.md second"; (2) CLAUDE.md learns its role and tools; (3) the relevant MOC in 02-Atlas/ gets a map of the domain; (4) hot.md learns what's urgent and why; (5) decision/learning notes for the reasoning. Hot vs cold is the discipline that keeps the agent from re-reading the entire vault every run — hot is a tight < 5 KB working set updated weekly, cold is the authority you reach for on demand. This is why a vault beats copy-pasting context: the agent navigates YOUR structure, not a flat list.
